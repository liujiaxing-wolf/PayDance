> 本手册用于把最终 PRD 转化为可执行的 Swift/SwiftUI 开发任务。当前只生成手册，不开始功能开发。

## 2. 开发环境

### 2.1 硬件与系统

- Apple Silicon Mac。
- 带实体刘海的 MacBook，用于正式 UI 验收。
- macOS 14.6 或更高版本。
- 至少准备另一种刘海尺寸的真机完成发布前验收。

### 2.2 Xcode

Atoll 当前 CI 使用 latest-stable Xcode，并明确说明源码需要 Swift 6.1+。开发机应使用支持当前源码的最新稳定版 Xcode，不再以 ReadMe 中较旧的“Xcode 15+”作为可靠下限。

先检查开发者目录：

```bash
xcode-select -p
xcodebuild -version
```

如果 `xcodebuild` 提示当前路径是 `/Library/Developer/CommandLineTools`，需要在本机安装完整 Xcode，并将开发者目录切换到实际 Xcode：

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

本手册生成时，当前机器仍指向 Command Line Tools，因此尚未执行 Atoll 的 `xcodebuild` 编译。切换属于系统级设置，应由开发者确认本机 Xcode 路径后操作。


## 5. 第一步：领域模型

### 5.1 枚举

建议模型：

```swift
enum SalaryMode: String, Codable, CaseIterable {
    case monthly
    case daily
    case hourly
}

enum LiveEarningsStatus: String, Codable, Equatable {
    case invalidConfig
    case restDay
    case beforeWork
    case working
    case lunchBreak
    case afterWork
}
```

星期不要直接把本地化显示文字写入配置。可以定义稳定枚举，再单独完成显示映射：

```swift
enum Weekday: Int, Codable, CaseIterable, Hashable {
    case sunday = 1
    case monday = 2
    case tuesday = 3
    case wednesday = 4
    case thursday = 5
    case friday = 6
    case saturday = 7
}
```

这里的原始值与 `Calendar.Component.weekday` 保持一致。界面顺序由本地化与地区决定，不能假定 Sunday 一定显示在第一位。

### 5.2 本地时间

```swift
struct LocalTime: Codable, Equatable, Comparable {
    let hour: Int
    let minute: Int
}
```

要求：

- `hour` 为 0 到 23。
- `minute` 为 0 到 59。
- 可转换为当天的 `DateComponents`。
- 不保存时区和日期。
- `endTime` 必须严格晚于 `startTime`。

### 5.3 配置

```swift
struct LiveEarningsConfig: Codable, Equatable {
    var schemaVersion = 1
    var isEnabled = false
    var setupCompleted = false
    var salaryMode: SalaryMode = .monthly
    var monthlySalary: Decimal?
    var dailySalary: Decimal?
    var hourlyRate: Decimal?
    var currencyCode: String
    var workdays: Set<Weekday> = [.monday, .tuesday, .wednesday, .thursday, .friday]
    var startTime = LocalTime(hour: 9, minute: 0)
    var endTime = LocalTime(hour: 18, minute: 0)
    var lunchBreakEnabled = false
    var lunchStart = LocalTime(hour: 12, minute: 0)
    var lunchEnd = LocalTime(hour: 13, minute: 0)
    var privacyModeEnabled = false
}
```

币种默认值通过 `Locale.current.currency?.identifier` 或等价系统能力获得。无法获得时使用明确的产品回退值，并为回退行为添加测试。

### 5.4 快照

```swift
struct LiveEarningsSnapshot: Equatable {
    let status: LiveEarningsStatus
    let earnedToday: Decimal
    let estimatedToday: Decimal
    let progress: Double
    let effectiveWorkedSeconds: TimeInterval
    let effectiveTotalSeconds: TimeInterval
    let secondsUntilNextTransition: TimeInterval?
    let generatedAt: Date
}
```

快照是计算结果，不遵循 `Codable` 也可以。禁止存入 UserDefaults 或历史文件。

### 5.5 本阶段完成条件

- 模型能编译。
- 默认值与 PRD 一致。
- 不存在夜班字段和固定月工作天数字段。
- 模型测试覆盖编码、解码和默认值。

## 6. 第二步：配置校验

`LiveEarningsValidator` 返回结构化问题，界面负责本地化：

```swift
struct LiveEarningsValidationIssue: Equatable {
    let field: Field
    let code: Code
}
```

至少校验：

| 字段 | 规则 |
|---|---|
| 当前薪资模式金额 | 存在、有限且大于 0 |
| 币种 | 有效 ISO 4217 代码或系统可识别代码 |
| 工作日 | 至少一个 |
| 上班时间 | 合法本地时间 |
| 下班时间 | 合法且严格晚于上班时间 |
| 午休 | 开启后开始早于结束，且完整位于工作时间内 |

切换薪资模式后，只校验当前模式的金额。其他模式已填写的值可以保存，但不能阻止当前模式提交。

无效配置不能覆盖最后一份有效配置。首次设置没有有效旧值时保持 `setupCompleted = false`。

## 7. 第三步：计算引擎

### 7.1 当前月工作日数量

`WorkdayCounter` 输入 `Date`、`Calendar` 和 `Set<Weekday>`，输出当前自然月匹配日期数量。

实现原则：

1. 使用传入 Calendar 获取当前月的日期区间。
2. 按天遍历，读取 `.weekday`。
3. 只根据用户选择的星期计数。
4. 不查询网络、节假日或请假。
5. 不使用固定 22 或 21.75。

必须测试：

- 28、29、30、31 天月份。
- 月初、月末。
- 只选一个工作日。
- 选择周一至周日。
- 不同时区和 Calendar 注入。

### 7.2 有效工作时段

当天时段只有两种结构：

```text
午休关闭
[上班, 下班]

午休开启
[上班, 午休开始]
[午休结束, 下班]
```

不要移植 PayDance 的 `night-shift.ts`、跨日标准化或 previous-day span 逻辑。

### 7.3 公式

使用最终 PRD 的公式：

```text
月薪日预计 = 月薪 / 当月工作日数量
日薪日预计 = 日薪
时薪日预计 = 时薪 × 当日有效总秒数 / 3600

月薪与日薪实时收入 = 日预计 × 有效已工作秒数 / 有效总秒数
时薪实时收入 = 时薪 × 有效已工作秒数 / 3600
```

上班前有效已工作秒数为 0；午休保持午休开始时的值；下班后等于有效总秒数。

### 7.4 纯函数接口

```swift
struct LiveEarningsEngine {
    func snapshot(
        at now: Date,
        config: LiveEarningsConfig,
        calendar: Calendar
    ) throws -> LiveEarningsSnapshot
}
```

Engine 内不得：

- 读取单例或 `Date()`。
- 访问 UserDefaults。
- 启动 Timer 或 Task。
- 格式化 UI 文案。
- 写日志。
- 发布 `@Published` 状态。

### 7.5 金额精度

- 公式内部使用 Decimal。
- 只在最终显示时四舍五入为两位小数。
- 不把已格式化字符串作为下一秒计算输入。
- 测试使用 Decimal 比较或显式容差，不依赖不可控的 Double 误差。

### 7.6 本阶段完成条件

- 月薪、日薪、时薪用例全部通过。
- 午休边界和状态边界用例通过。
- 当前月工作日统计用例通过。
- 任何有效输入都满足 `0 ≤ earnedToday ≤ estimatedToday`。
- Engine 测试不依赖系统当前时间。

## 8. 第四步：存储与 Controller

### 8.1 Store

`LiveEarningsStore` 是配置唯一读写入口。建议职责：

- 加载配置。
- 校验后保存。
- 关闭功能但保留配置。
- 清除配置。
- 为未来 schemaVersion 提供迁移入口。

沿用 Atoll 的 `Defaults` 包。可以让配置符合 `Defaults.Serializable`，或用单独的版本化 Data 编码。不要把薪资金额拆成散落在多个 SwiftUI View 中的 `@AppStorage`。

### 8.2 Controller

```swift
@MainActor
final class LiveEarningsController: ObservableObject {
    @Published private(set) var snapshot: LiveEarningsSnapshot
    @Published private(set) var config: LiveEarningsConfig
}
```

Controller 负责：

- 调用 Engine。
- 发布当前快照。
- 根据状态安排下一次刷新。
- 监听配置、日期、唤醒、时区、锁屏和解锁事件。
- 功能关闭或对象销毁时取消 Task、Timer 和通知观察者。

### 8.3 调度策略

| 状态 | 调度方式 |
|---|---|
| working | 最多 1 Hz |
| beforeWork | 调度到上班时间 |
| lunchBreak | 调度到午休结束 |
| afterWork | 调度到下一次日期变化 |
| restDay | 调度到下一次日期变化 |
| invalidConfig | 不自动高频重试，等待配置变化 |
| disabled | 不保留实时收入任务 |

使用可取消的 Task 或统一 Timer，不允许每次 SwiftUI `body` 变化都创建新计时器。

唤醒、解锁和系统时间变化后直接重算，不补播离线期间的每秒动画。

### 8.4 生命周期测试

至少验证：

- 连续启用、关闭、再启用不会叠加计时任务。
- 更新配置后旧调度失效。
- Controller 释放后不继续发布。
- 午休时没有 1 Hz 无意义计算。
- 休眠恢复后只产生一次立即重算。

## 12. 第八步：关闭态刘海

主要修改：

```text
DynamicIsland/ContentView.swift
DynamicIsland/components/Notch/
DynamicIsland/managers/FlyoutFrameCalculator.swift
DynamicIsland/sizing/
```

### 12.1 先做显示策略

不要直接在当前 `else-if` 链里插入 `LiveEarningsClosedView`。先新增纯策略：

```swift
enum ClosedNotchPresentation: Equatable {
    case systemOverride
    case mediaWithEarnings
    case earningsOnly
    case originalAtoll

```

策略输入至少包括：

- 功能是否启用并完成配置。
- 今天是否为工作日。
- 隐私模式和锁屏。
- 当前快照状态。
- 是否有媒体会话。
- 是否有高优先级隐私或关键系统事件。
- 当前是否处于打开状态。

### 12.2 优先级

```text
高优先级隐私和关键系统事件
用户主动打开的界面
右侧实时收入
左侧媒体摘要和普通状态
```

普通媒体不能把收入数字完全替换掉。高优先级事件结束后，必须调用 Engine 重新计算当前金额。

### 12.3 右翼布局

`LiveEarningsClosedView` 要求：

- 只显示 `128.46` 形式的数字。
- `.monospacedDigit()`。
- 右对齐。
- 固定两位小数。
- 变化位滚动。
- Reduce Motion 时直接替换。
- 长数字通过最小缩放因子适配，不显示 K、M。

收入视图增加了实体刘海右侧宽度。必须同时核对：

- 关闭态面板宽度。
- `dynamicNotchSize`。
- right wing width。
- 悬停激活宽度和点击区域。
- 全屏、Spaces 和不同缩放比例。
- 展开与收起时的 matched geometry 或 transition。

只加 overlay 会产生裁切和热区不一致，禁止作为正式实现。

### 12.4 媒体共存

有媒体时：

```text
[左翼：封面或媒体指示] [实体刘海黑区] [右翼：实时收入]
```

无媒体时：

```text
[空或 Atoll 原有左侧状态] [实体刘海黑区] [右翼：实时收入]
```

高优先级系统事件出现时可以替换整个关闭态。事件结束后恢复上面两种组合之一。

## 13. 第九步：隐私与锁屏

### 13.1 手动隐私模式

- 设置页和 Home 提供同一个配置开关。
- 开启后关闭态恢复 Atoll 原有内容。
- Home 卡片保留结构，但不显示具体金额。
- 关闭后立即从当前时间重新计算。

### 13.2 锁屏

复用 `LockScreenManager.shared`。实时收入不新增锁屏 Widget：

- 锁屏时禁止关闭态和锁屏面板暴露薪资。
- 解锁不自动关闭用户手动开启的隐私模式。
- 解锁后重算快照。

### 13.3 日志

禁止：

```swift
print(config)
logger.debug("salary: \(amount)")
assertionFailure("invalid salary \(amount)")
```

允许记录不含敏感值的状态码，例如配置解码失败、Engine 返回校验错误、Controller 完成生命周期清理。

## 14. 第十步：格式化、本地化与动效

### 14.1 金额格式

保存币种代码，显示时分两种格式：

```text
关闭态：128.46
Home：¥128.46 或 $128.46
```

Phase 1 固定两位小数。Home 使用系统本地化分组符和币种位置；关闭态去掉币种并保持稳定宽度。

### 14.2 时间格式

- 设置中的时间选择器跟随系统 12/24 小时偏好。
- 内部保存小时和分钟。
- 剩余时间使用本地化 duration，不手写中文单位拼接。

### 14.3 String Catalog

所有文案进入 `DynamicIsland/Localizable.xcstrings`。至少包含：

- 功能名和首次启用说明。
- 薪资模式、金额、币种和工作日。
- 午休、隐私和本地数据说明。
- 状态文案。
- 表单校验错误。
- 清除确认。
- VoiceOver 标签。

其他语言没有翻译时回退 English。不得用中文作为代码逻辑键。

### 14.4 滚动数字

动效只作用于变化位。建议先把格式化后的字符串拆分为字符槽位，再按旧值与新值决定变化动画。

必须处理：

- `9.99` 到 `10.00` 的位数变化。
- `99.99` 到 `100.00`。
- 休眠后大幅跳变。
- 午休冻结。
- 下班时最终值。
- Reduce Motion。

## 18. 常见错误

### 18.1 把 PayDance 当前实现直接翻译成 Swift

PayDance 当前包含固定 `workDaysPerMonth`、09:30 至 18:30 和夜班。最终 PRD 已改变这些规则。开发只能复用思想和测试方法，不能机械翻译现有字段。

### 18.2 在 ContentView 的互斥链里再加一项

这样会让收入与媒体互相替换，无法实现左媒体、右收入。先抽显示策略和组合布局。

### 18.3 用 overlay 填右侧白框

视觉上可能暂时出现数字，但窗口宽度和命中区域没有变化，容易裁切、闪烁或无法触发悬停。正式实现必须参与刘海尺寸计算。

### 18.4 每秒保存金额

实时金额可以从时间和配置重算。每秒保存会增加写入、隐私和恢复复杂度，也会在时间调整后产生错误。

### 18.5 VoiceOver 每秒播报

视觉更新不等于可访问性通知。只在用户聚焦或主动查看时提供当前金额和状态。

### 18.6 把本地保存写成“已加密”

沿用 Defaults 只能声明本地保存。没有实现并验证加密前，不得在产品文案中声称加密。

### 18.7 忽略 Minimalistic UI

Home 和关闭态已有多种模式。至少要保证收入功能在用户可选的现有模式中有明确表现，不能只测试一种默认布局。
