# 开发与提交规范

## 1. 分支策略

- 稳定验收基线：`第二阶段开发最终版`。
- 新功能：从稳定基线创建 `feature/<short-name>`。
- 缺陷：`fix/<short-name>`。
- 文档：`docs/<short-name>`。
- 不直接重写 `第一阶段开发最终版` 和 `第二阶段开发最终版` 历史。

## 2. 开发流程

1. 明确需求 ID、范围和验收标准。
2. 更新或新增 ADR、安全/数据影响和测试计划。
3. 先编写可测试规则或接口，再接 UI。
4. 小步提交，保持每个提交可构建。
5. 完成自动回归、Debug 构建和相关真机用例。
6. 同步文档、追踪矩阵和变更记录。
7. 用户验收后再创建阶段最终分支或发布标签。

## 3. Swift/SwiftUI 约束

- UI 状态优先使用明确的 Observable/State 边界，避免多个计时器和重复订阅。
- I/O Store 使用 actor 或专用队列，不阻塞主线程。
- 所有日期规则基于显式 Calendar、Locale 和 LocalDate。
- 需要跨线程的回调明确 MainActor 边界；逐步消除 Swift 6 并发警告。
- View 不包含工资公式、文件格式解析或 ScreenCaptureKit 生命周期逻辑。
- 可访问性标签描述“结果和动作”，计时变化不应每秒打断 VoiceOver。

## 4. 提交信息

推荐格式：

```text
feat: 增加……
fix: 修复……
style: 调整……
test: 补充……
docs: 更新……
refactor: 重构……
```

提交正文说明为什么改、风险和验证方式。不要在提交信息中写 Key、工资或私人事项。

## 5. Pull Request 最低内容

- 关联需求 ID 和 ADR（若有）。
- 变更范围与明确非范围。
- UI 前后对比或真机说明（不得泄露个人内容）。
- 自动测试和构建结果。
- 权限、数据、迁移、许可证影响。
- 回滚方式。

## 6. Review 清单

- 是否破坏 Atoll 原有 Home/导航/关闭态？
- 是否产生新的网络请求、权限或敏感数据？
- 是否在多个地方重复计算同一事实？
- 是否处理空状态、权限拒绝、文件失败和取消？
- 是否有单击/双击、悬停/转场或窗口生命周期竞争？
- 是否在最小系统版本可编译？
- 是否同步文档和测试？
