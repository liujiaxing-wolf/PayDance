# 文档管理规范

## 1. 目的

保证文档与代码、产品状态和验收结论同步，避免出现“文档说未开发、代码已经发布”或“代码变了、验收标准没变”的情况。

## 2. 文档元数据

正式文档至少包含以下信息中的适用项：

| 字段 | 要求 |
|---|---|
| 文档名称 | 与文件标题一致 |
| 版本 | `主版本.次版本`，重大范围变化提升主版本 |
| 状态 | 草稿、评审中、已批准、已归档 |
| 日期 | 使用 `YYYY-MM-DD` |
| 适用代码基线 | 分支和短提交号 |
| 维护人 | 未指定时写“项目维护者”，不可虚构姓名 |
| 相关资料 | 使用相对链接，外部规范可用 HTTPS 链接 |

## 3. 文件与目录命名

- 一级目录按生命周期编号排序，如 `02-产品需求`。
- 文件使用 `NN-中文名称.md`，避免“最终版2”“新新版本”等名称。
- 历史基线不覆盖原文件；通过索引说明状态。
- 图片放在相邻的 `assets/`，文件名使用小写英文、数字和短横线。

## 4. 内容结构

除短索引外，建议采用：

1. 文档信息；
2. 目的和范围；
3. 主体内容；
4. 验证或完成标准；
5. 风险、限制或待决策项；
6. 相关文档；
7. 变更记录。

操作手册必须给出前置条件、步骤、预期结果、失败处理和回滚方式。参考文档应准确、简洁，不混入大量教程。

## 5. 状态与审批

```text
草稿 → 评审中 → 已批准 → 已归档
                 ↘ 变更后重新评审
```

- 产品范围变更：由产品负责人确认。
- 架构、安全和数据边界变更：由维护者完成代码事实核对。
- 验收报告：只有用户明确确认后才能标记“通过”。
- 发布记录：只有完成实际部署或发布后才能填写地址、版本和签名状态。

## 6. 代码变更同步矩阵

| 变更类型 | 必须同步的文档 |
|---|---|
| 新功能/删除功能 | 产品基线、追踪矩阵、用户手册、测试、变更记录 |
| 数据结构/存储位置 | 数据生命周期、安全隐私、迁移与回滚 |
| 新权限/网络服务 | 配置权限、威胁模型、隐私说明、发布清单 |
| 架构调整 | 系统架构、代码导航、ADR |
| 发布流程调整 | 部署手册、发布回滚、维护手册 |
| 依赖或许可证变化 | 第三方依赖与许可证、NOTICE（如适用） |

## 7. 链接和事实检查

提交前至少执行：

```bash
git diff --check
```

并人工确认：

- 相对链接可以从当前文档打开；
- 命令与当前工程一致；
- 分支、提交号、最低系统和范围没有过期；
- 示例不含真实 API Key、工资、日历内容和个人路径以外的敏感信息；
- “已完成”“已发布”“已通过”都有证据。

## 8. 维护周期

- 每次功能合并：检查受影响文档。
- 每次阶段验收：更新验收报告、风险和结项状态。
- 每次正式发布：更新版本、变更记录、部署和回滚信息。
- 每季度或恢复开发前：做一次链接、依赖、权限和范围复审。
